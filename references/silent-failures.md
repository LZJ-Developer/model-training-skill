# 静默故障：从主张反推可证伪检查

本协议处理一类问题：**程序继续运行、常规信号看似正常，但数据、计算或评测已偏离任务契约**。有效载荷损坏只是其中一种；索引错位、未更新的分支、失真的损失和陈旧指标也可能同样静默。它们不必涉及硬件位翻转，不能都狭义归为 silent data corruption。

本次 embedding 事件是检验协议的一个案例，不定义协议的全部范围。具体文件适配器见 [payload-integrity.md](payload-integrity.md)；诊断方法见 [diagnostics.md](diagnostics.md)。

## 1. 原理：补上能区分正确与错误的观测

运行成功记为 `R`，任务所需正确性记为 `C`，则 `R=1` 不推出 `C=1`。同样，loss 下降不推出所有输入被正确消费、所有分支都更新，或评价量就是所声称的能力。

如果健康状态 `h` 与某种故障 `f` 在当前观测 `O` 下相同，即 `O(h)=O(f)`，继续重复这些观测不能区分它们。需要增加**对该故障有区分力**的检查。例如大小/shape/dtype 可能同源于一个正确 header，六项全绿也未增加关于内容或实体对应的证据。

执行者应先提出“哪个假设错了仍会出现当前现象”，再找低成本、能排除该替代解释的观测。观测不必总是更多日志：可能是一个独立锚点、真实路径上的计数、精确可解小任务、有效干预或故障注入。

## 2. 最小闭环：主张 → 前提 → 检查 → 动作

按当前任务执行以下步骤，不机械遍历所有故障。新数据/组件/运行方式、已有异常或高成本扩展，才决定哪些边界需要新增检查；身份与适用范围未变的有效证据可以复用。

1. **明确本次要支持的主张。** 如“模型使用了新模态”“该分支改善未见扰动”“修复件已被训练消费”，不能只写“训练没问题”。
2. **列出使该主张成立的少数关键前提。** 沿实际依赖链定位数据、索引/缓存、loader、前向、loss、optimizer、checkpoint、评测与报告的相关边界。优先检查改动处、共享基础设施和一旦错误就会改变结论的环节。
3. **把前提变成可执行条件。** 写明输入/环境与适用范围、可观测量、预期关系或容差依据、失败及无法检查时的动作。避免所有条件都从同一个可能错误的实现/元数据推导。
4. **验证检查本身。** 至少用已知有效例检验不会总拒绝，再用针对该前提的隔离故障检验能够失败；有合适数学性质时增加变形关系。故障注入不得污染原始数据、正式缓存或最终测试。
5. **接入相应执行边界。** 检查函数或命令必须由真实路径调用并传播失败：数据验证放在消费前，参数成员关系放在构建 optimizer 后，更新行为在首个有效更新后，指标自检在用它选 checkpoint 前。离线演示通过不等于真实训练已受保护。
6. **记录证据与范围。** 把报告与运行身份关联；结论限定于实际检查到的条件。异常先保全和定位，再做有界修复，不把不明原因的改进编写成机制。

检查条件可写成一条紧凑记录，不要求搭建新平台：

```text
claim / assumption: 本次主张及它依赖的前提
boundary / scope:   实际输入、阶段、实体/参数/指标范围
observer:           真实命令/函数与独立参照来源
predicate:          预期关系或带依据的范围；未知项明确记录
controls:           健康例、针对性故障例、适用的变形关系
result:             pass | fail | unknown | skipped，附来源与检查身份
action:             继续 / 阻断受影响阶段 / 已授权的显式降级
```

## 3. 同一方法跨不同故障层使用

以下是候选模式，不是每次都要跑的测试清单。具体检查须匹配模型、任务和授权预算。

| 故障层与正常表象 | 更有区分力的最小检查 | 合法例外与结论边界 |
|---|---|---|
| 内容退化：文件可读、shape 正确，但零填充/常量占位 | 内容分层统计或来源核验；健康例与保持元数据不变的坏块注入 | padding/稀疏零可能合法；非零也不证明语义正确。文件探针只是一个适配器 |
| 语义/消费错误：健康向量被错配，或 worker 仍读旧 cache | 独立已知 ID→row→值锚点，真实 loader 前后对应与 lookup/fallback 计数；注入映射置换或旧版本 | 同分布、同源文件 hash 不排除错位；只检查几个 batch 不能声明全消费范围正确 |
| 分支未训练：loss 依靠其他通路下降，目标参数漏出 optimizer/被 detach 或 mask | 核对预期可训练参数与 optimizer 对象身份；有效样本上的梯度、实际参数差异和激活后干预；故障中移除该组或关 gate | 冻结、稀疏路由、零初始化、AMP 跳步可合法不更新。检查预期活动子集，不要求每个参数每步非零 |
| 目标被改写：mask/归一化/权重错误仍产生平滑 loss | 小型可解样例与有效计数；对照目标定义检查不等权 microbatch/末尾窗口；注入漏 mask/错误分母 | 累积与大 batch 的等价只适用于定义和样本交互允许的情况，不强加给 BatchNorm/对比损失 |
| 评测/状态错误：陈旧 checkpoint、恒定/反向指标、错误 join 仍有漂亮分数 | 记录实际载入权重、预测与 evaluator 身份；已知精确/基线/错误预测例及行对应；注入 stale metric 或错误 checkpoint | oracle 是隔离诊断，不计入可部署分数；代理指标排序和不同评价版本需单独验证 |
| 汇总掩盖失败：总体均值改善而关键亚组无覆盖或退步 | 同一分母下的覆盖数、分量/分组配对差与失败组；构造“大组提升、小组退化”的聚合对照 | 小组方差和任务权重必须说明；不要求所有组都涨，也不把不可区分当等效 |

通用原则是**测试承载主张的关系，而非只测试合法数值**。例如模型按设计逐样本独立时，batch 顺序置换应使输出对应置换；集合交互、训练态 BatchNorm 等改变了前提时，必须另选关系。不能套用不适用的“万能变形测试”。

独立性要落实到参照来源：审计与生产路径若共用同一错误映射，三份一致结果仍可能共同失真。使用独立 ID 清单、手算 fixture 或已核验锚点；应训练的模块清单不能仅由 optimizer 自己生成。参数变化也可能仅来自 weight decay 等因素，需结合有效任务梯度和行为验证。

例如契约定义全局有效目标 MSE：两个 rank 分别有 1000、10 项有效目标，局部 MSE 为 1、9，正确聚合是 `(1000×1 + 10×9) / 1010 ≈ 1.0792`，不是两个均值再平均得到的 5。这个小例可经过真实 reducer 检验分母语义；如果任务原本定义等组宏平均，则 5 反而可能正确，不能仅凭数值判断。类似地，在直接比较响应差的 MSE 中，预测恰等于目标的 fixture 应得 0；若正式评测仍给非零，先查表示变换与 join，而非判模型方法失效。

## 4. 状态、阻断与身份

- `pass`：该条件在所记录范围内得到支持；不是系统无故障的证明。
- `fail`：观测违反条件，阻断依赖它的阶段或主张，保留可追踪错误。
- `unknown`：参照缺失、检查中断、覆盖不足或身份不符，不能当成 pass。
- `skipped`：记录原因与适用性；确实不适用的检查可以跳过，尚未执行的必需检查不能借此放行。

必需前提的 fail/unknown（包括检查程序异常）阻止受影响的昂贵阶段或结论；不阻止无关的安全取证。可选组件只有在任务已允许降级时显式关闭/替代，并记录新配置与科学范围。不能静默补零、吞异常后继续标成完整模型。

管线健康与方法有效分开判断：检查通过不保证方法有增益；在可信管线上得到的负结果可以成立。检查本身连健康阳性对照都未通过时，应先修检查，不能直接归罪于生产数据或模型。

检查的有效性依赖上下文：数据/内容版本、有序映射、代码/生效配置、checkpoint/运行状态、采样范围、检查实现与 policy。相关依赖变化后重新检查，不能仅因“同一路径上次 pass”复用报告；也不必因不相关文件变化重跑全部昂贵检查。只读 mmap、一次 hash 或前后 stat 不能替代不可变数据与并发写入约束。

运行时保留少量最有区分力的计数：有效样本/目标、lookup miss/fallback、预期活动分支、实际 optimizer 更新/AMP 跳步、指标更新时间与覆盖。按阶段/风险采样；日志体积和观察开销也受预算约束。新异常先定位，不能用一个跨任务固定百分比自动判死所有通路。

## 5. 事故复盘：修复、影响和科学结论分开

先保存可疑输入、运行状态和日志，再沿依赖定位最早违反条件的边界；优先做能区分原因的小实验，而不是先调参、重写架构或广泛重跑。必要时再检索参考实现，已有有效调研可复用。

按 `artifact/配置/状态 → 实际消费或执行范围 → run/checkpoint → claim` 追踪影响，把结果分成已确认影响、可能影响和未见证据。发现一个坏件不等于全部历史实验无效；一条修复对照也不恢复所有主张。无法追溯的记录应标为待核验。

修复产生新版本，保留旧证据并使依赖缓存/报告失效。在可比初始状态、代码、切分和预算下验证修复；明确改变的因素与剩余差异。数据、optimizer 或评测错误的修复会自然改变后续轨迹，不能要求权重逐步相同。使用开发协议复核受影响主张，最终测试响应仍不用于选修复方案。

交付应同时说明：什么故障被复现；哪个检查现在会失败；真实启动/更新/选型路径是否已接入；哪些结论已复核；还有什么未被覆盖。**“增加了检查文档”“合成测试通过”“生产路径已接入”“科学主张得到重验”是四种不同完成状态。**

## 6. 当前仓库的验证边界

本 PR 的可执行 `.npy` 探针及故障注入测试验证“有效载荷内容退化 → 非零退出 → 假训练不启动”这一适配器。它不能自动验证任意框架的索引、optimizer、loss 或 evaluator；这些检查要绑定宿主真实路径与任务契约。

其他层以独立行为演练检查 skill 的决策与证据边界；演练不是宿主实现测试或真实训练结果。扩展时优先为新出现的关键故障补一个有区分力、能失败的检查，不积累一份所有项目每次都执行的大全清单。
