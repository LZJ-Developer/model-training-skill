# 超参、数值实现与预算

本文件提供选择方法，不给脱离任务的“最佳默认值”。任务契约与四道检查以 `SKILL.md` 为准；配置、实验比较及运行产物以 `run-artifacts.md` 为准。维护者的脱敏案例用于提出候选值，不代表其他任务已验证这些值。

## 1. 优化器与调度

先复用当前任务可运行、版本明确的配置；核对源码与配置是否一致，记录来源。没有可靠参照时，选择与参数化、损失和硬件兼容的简单起点，再做小预算验证。

| 项 | 选择依据 | 不可直接推广的经验 |
|---|---|---|
| 优化器 | 当前参数化、稀疏性、已有实现与对照 | AdamW 可作为候选，不保证解决所有不收敛 |
| 学习率 | 实际更新量、数值稳定性及验证学习曲线 | 适配器可把 3e-5 / 1e-4 / 3e-4 作为候选示例；范围须根据目标尺度和实现调整 |
| weight decay | 参数组、正则需求与验证证据 | 小样本不自动意味着较小 wd；先区分过拟合和优化不足 |
| β、eps | 优化器定义、状态精度、数值范围及版本 | bf16 不自动要求 β2=0.95 或 eps=1e-10 |
| 梯度裁剪 | 裁剪前范数分布、损失归一化与更新稳定性 | 阈值 1 或 10 都不是跨任务常数 |
| batch 与累积 | 显存、吞吐、独立背景覆盖、优化噪声和 batch 内交互 | 改 batch 可能改变质量；需要验证 lr 与采样，不能只当速度旋钮 |
| 调度 | 可用步数、初始状态与验证结果 | 常数 lr、warmup、cosine 都是候选；适配器没有通用 warmup 百分比 |
| 精度 | 设备/算子支持、预训练权重、目标与 loss 的动态范围 | bf16、fp16、FP32 按 §2 选择，不按“新卡/老卡”简单划分 |

比较调度时固定其余条件，并核对 scheduler 按 micro-step 还是 optimizer step 更新、恢复训练后状态是否正确。尾部衰减可能改善也可能损害当前指标；不要把脱敏案例中的相关现象写成确定机制。

## 2. AMP、梯度累积、裁剪与 GC

### 2.1 精度

先在代表性小切片上保留 FP32 参照，再检查 AMP 的有限值、损失/梯度差异、吞吐、显存与验证行为。使用当前安装版本支持的 `torch.autocast` / `torch.amp` 接口，不能只根据文档最新版本修改现有环境。

- bf16 需设备和算子支持；其动态范围与 fp16 不同，但精度更低，仍需验证数值行为，通常无需 GradScaler。
- fp16 训练通常配合适用设备上的 GradScaler；缩放不能修复前向溢出、非法目标或不稳定 loss。
- 敏感的概率、计数似然、差分和归约可在 FP32 中计算；必要时局部禁用 autocast。不要未经检查将整个模型、输入和 optimizer 状态统一转成低精度。

设备支持、算子转换和梯度缩放边界见 [PyTorch AMP](https://docs.pytorch.org/docs/stable/amp.html)。

### 2.2 梯度累积按目标权重归一化

先写出要优化的目标。对一个有效更新窗口，若固定数据权重为 `w_jk`，有效监督损失为 `ell_jk`，则：

```
S_j = Σ_k w_jk * ell_jk
W_j = Σ_k w_jk
L_window = (Σ_j S_j) / (Σ_j W_j)
```

权重单位可以是样本、背景、有效基因或任务项，必须符合契约；它们不是默认等价的。若 `L_j = S_j / W_j`，每个 microbatch 对梯度的贡献应为 `L_j * W_j / W_window`。仅在每个 microbatch 的权重相同、窗口恰有 K 个 microbatch 时，才退化为 `(loss / K).backward()`。

- 掩码覆盖或 microbatch 大小不同时，不能平均各批均值后当作全窗口均值。
- 末尾不足 K 批时，按实际有效权重归一化并完成更新，或显式丢弃且记录策略；不能仍除以计划 K 后声称等价。
- 无有效监督的窗口要显式处理；不同 loss 项若各自有分母，分别归一化后再按定义组合。参数正则也需按目标加入，避免每个 microbatch 重复累计。
- 分母未知时，可累积未归一化的分子梯度，再按窗口权重处理；先核对实现。依赖模型参数的权重/分母不能套用“固定数据权重”推导。
- 分布式训练还要核对各 rank 的有效权重及梯度平均/求和约定；本地均值的平均未必等于全局加权均值。
- 梯度累积与单个大 batch 在 BatchNorm、batch 内对比损失或交互存在时不一定等价。

AMP 下在整个有效窗口中保持同一缩放因子，累积完成后按顺序执行：

1. 使用 scaler 时对相应 optimizer 执行一次 `unscale_`；
2. 如采用分子梯度累积，完成约定归一化；检查真实梯度并记录裁剪前范数；
3. 按需裁剪，再执行 optimizer/scaler step；
4. 更新 scaler、按定义推进调度，并清零梯度。

不要在每个 micro-step 提前 unscale 或裁剪；记录 AMP 跳步，区分计划步数与实际更新数。具体 AMP 时序见 [PyTorch：梯度累积与裁剪](https://docs.pytorch.org/docs/stable/notes/amp_examples.html#gradient-accumulation)。

### 2.3 GC 仅在测量后优化

不默认在首步后执行 `gc.freeze(); gc.disable()`。只有 profiler 确认 GC 停顿构成瓶颈、检查循环引用与内存增长、并能恢复原状态时，才试验调整。记录前后内存和耗时，在结束或异常路径恢复先前启用状态；若使用 freeze，还需处理相应 unfreeze。

`freeze` 会把受跟踪对象移入不参与后续收集的永久代，官方描述包含 fork 场景；它不是通用训练加速保证。参见 [Python GC 接口](https://docs.python.org/3/library/gc.html)。

## 3. 可训练容量与数据支持

不按“少于 10K / 10K–100K / 超过 100K 行”决定模型类型，也不使用通用 30:1 参数/样本比上限。

同时记录：可训练/总参数量、监督行数、独立 donor/背景/实验重复数、扰动与剂量/时间覆盖、相关性、目标噪声及预训练分布。多基因向量增加响应维度，同 donor 多细胞可能提高测量精度；二者都不能直接换算成独立生物样本数。

用任务内学习曲线、训练/验证差距、容量或秩消融、基线和预算比较以下候选：

- 线性探针或正则化回归；
- 冻结主干加适配器；
- 部分解冻；
- 在数据与预算支持时全量微调。

冻结的理由可以是成本、保留表征与限制自由度；其效果需要验证，不能预设优于全量。若主张预训练贡献，需要与适当随机初始化或其他表征对照，并说明训练预算和调参机会是否可比。

## 4. 记录配置选择与偏离

在配置及运行产物中引用所选值、候选范围、来源和理由；格式由 `run-artifacts.md` 维护。特别说明：

- loss 的单位、有效权重、掩码、各项归一化与手工权重；
- microbatch、累积、分布式归约及末尾窗口；
- 精度、optimizer 参数组、梯度裁剪、调度与恢复状态；
- 相对参考实现的偏离及其依据是源码、测量、文献还是待验证假设。

文档和代码不一致时先核实实际生效配置；不能仅因“代码较新”就认为它科学上正确。

## 5. 损失权重

权重先来自任务目标与归一化单位，再由验证实验调整。不同项默认权重都为 1 不代表影响相等；频率反比权重会改变目标总体，并可能放大稀有组噪声。

先检查各项有效数、尺度、梯度及分组覆盖，再选择等背景、等扰动或其他契约定义的权重。上限和候选范围需有任务依据；类别频率法不自动适用于连续基因响应向量。

若损失权重是当前瓶颈，可以提前做有界对比；不要求机械放在所有调参之后。未测量前不能声称 sweep 只需固定 GPU·h，也不能从“少有人扫过”推断可发表性。

## 6. 按真实管线估预算与推进

冻结主干仍可能需要昂贵前向，激活、序列长度、I/O、渲染和评测也会主导成本。**不能按新增可训练参数比例线性推算训练费用。**

1. 在授权资源上用代表性切片测启动/编译、数据准备、稳态 optimizer step、评测/渲染及保存 checkpoint 的耗时；记录实际硬件、精度、形状、吞吐、峰值显存和主存。
2. 用实际 step 时间估训练部分，单独加入数据/缓存构建、评测频率、种子/折数、失败重跑及资源计费开销。异步 GPU 计时使用合适的同步、事件或 profiler，不能只计 Python 提交时间。
3. 根据测量给范围和假设；分布式利用率、动态形状及大数据 I/O 未测时标为不确定。计费依实际资源占用与价格计算，GPU·h 不是所有平台的完整账单。
4. 先安排能改变决策的小实验，再依据学习曲线与不确定性决定扩展。多种子/多折次数按要回答的问题与可用预算规划，不机械指定每臂三种子。
5. 用户已明确授权的设备、GPU·h/费用上限与操作范围内，可按检查结果自主推进并记录剩余预算，不逐步重复询问。未知正式付费预算、将超出上限或需要更高资源权限时，先完成可用的本地检查、形成具体计划，再对齐必要边界。

继续、停止或扩大规模的判据以 `SKILL.md` 的任务契约与门禁为准；对未超过基线的 pilot，先区分实现问题、优化不足、预算不足和方法局限，不能把一次小预算负结果推广为方法无效。

## 7. checkpoint 与选择偏差

在验证层用与主张相关、预先定义的指标或代理指标选 checkpoint；代理需说明理由与已知偏差。多基因响应若需渲染后评分，应核对读数层与最终评分层是否一致，而非默认二者排序相同。

- checkpoint、超参、阈值和校准方案用验证证据选择；校准参数在指定开发分区拟合，其拟合分数不当独立验证，详见 `perturbation-evaluation.md` §3。最终测试只用于锁定方案后的独立确认。
- 如果最终测试已参与选择，应如实标记，并另设未使用的确认集或采用适当的嵌套评估；不能靠改名恢复独立性。
- 监控项、方向、更新频率与缺失行为需验证，避免 stale metric 让 best checkpoint 停在早期。
- 同时记录处理 batch 数、有效 optimizer step、AMP 跳步及调度步；恢复训练时核对 checkpoint 中的模型、optimizer、scheduler、scaler 与随机状态。
