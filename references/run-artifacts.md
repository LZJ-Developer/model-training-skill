# 运行产物

一次长训练（>1 小时、方法较新、可能无人看守）应该留下四样东西。短的一次性排障调用不需要。

目的只有一个：**一个拿到目录的陌生人，不读你的大脑，也能重建这次运行并自己判断它对不对。**

---

## 1. 目录

```
outputs/<date>_<slug>_<seed>/
  config.yaml        解析后的完整配置（不是模板，是实际生效值）
  provenance.json    commit、argv、环境版本
  run.md             由训练入口写出，见 §2
  metrics.tsv        矩形表，每行一步，见 §3
  demos/             每个阶段的完整样本
  ckpt/
```

`config.yaml` 必须是**解析后**的值。抄模板配置等于没有记录：默认值、环境变量、命令行覆盖都不在里面。

---

## 2. `run.md`：由脚本写，不是手写

手写的总结会漏掉「当时觉得不重要」的东西，而那些恰好是三个月后要用的。让训练入口在每个阶段结束时追加一段。

每个阶段的结构：

```
## <阶段名> · <面包屑，例如 step 300 / epoch 3>
<耗时>，<峰值显存>
<这一阶段的完整样本，原始形态 + 模型消费形态>
<指标表，30–60 行>
```

规则：

- **样本先于指标读。** 完整的输入/输出样本是第一道 sanity check；指标在它之后。
- 第一个训练样本和第一个评测样本都要留**原始形态**和**模型实际消费的形态**（张量形状、掩码、特殊标记）。这两者不一致是最常见的静默 bug。
- 长输出不要截断。失败、截断、重复、饱和的输出必须原样保留——那些才是有信息的。
- stdout 保持稀疏，只打印日志路径。
- 末尾重新给出一个紧凑结果块：headline 指标、可复制的完整结果表、输出路径、run 身份（commit + seed + 配置哈希）。

---

## 3. 指标表

一列一件事，有对照组时用同一张表。

| 规则 | 理由 |
|---|---|
| 第一列是索引，链接到来源 | 别人要能点回原始记录 |
| 接着是短元数据（seed、步数、改动项） | 表格本身要能自我解释 |
| 然后是 headline 分数**和它的输入** | 只给分数无法复查 |
| 按 headline 排序 | 读者第一眼看到结论 |
| 每个表头带方向箭头 | 否则「0.72 是不是好」无法判断 |
| 加粗真正有意义的列最优值 | 防止把噪声当最优 |
| 基线与对照用斜体 | 它们不是手段，是标尺 |
| 包含 floor（平凡基线） | 没有 floor 的分数没有意义 |

---

## 4. `MENTAL_MODEL.md`：一页，两节

```markdown
## Current model
最好的解释、不确定的地方、以及它的预测。
（错但可证伪的模型 > 不可证伪的模型）

## Dated clues
还没有被当前模型解释的观察。每条：日期、阶段/条件、来源日志链接。
观察与推测分开写。
```

维护规则：

- **每一轮开始时读它。**
- 线索被吸收后，从待处理区移除，但原始观察必须仍留在日志里。
- **保留未解决的矛盾。** 不要为了让解释自洽而改写观察。
- 新观察进 `Dated clues` 时，引用具体的日志行。

三个检查，每次运行前后各做一次：

1. **回测**：最近几次结果，这个模型事先会不会预测对？每一次没预测对，是哪个信念导致的？改那个信念，并引用日志行。
2. **上限**：这个方法每个部分的**最好情况**是多少（它模仿的目标、可用的 oracle、参考实现）？在当前评测上量过吗？没量过就写「没量过」。
3. **预测记录**：模型的品质是它预测对的记录，不是它的篇幅。

## 5. 运行前：选项表

在 `MENTAL_MODEL.md` 里，每次运行前修正一次并展示。

| 选项 | 应该影响哪个指标 | 方向与量级 | 可能结果 → 模型更新 | GPU/时长 |
|---|---|---|---|---|

- 架构与损失改动只要在这个问题上是活选项，就要在表里——不要只列优化器设置。
- 用粗略判断，不要编造信息增益分数。
- 写清这次运行改了哪几项、为什么。**每项都有自己独立的指标时，一次改多项是可以的**（长训练的常见做法）；此时你学到的是「在其余改动存在的前提下，每项的效果」，要按这个口径记录。
- 展示与对照运行的 `config` 差异。

---

## 6. 运行前：预测表

先用一句话写下「这次运行回答什么问题」，再写「什么结果会改变当前的解释」。

| 可能出问题的部分 | 预期看到什么 | 太弱 | 太强 | 有 bug | 指标存在吗 |
|---|---|---|---|---|---|

- 最后一列写「不存在」的，先把它加进训练脚本。
- 对照组至少包含：基线模型在同一输入上的结果；随机方向 / 打乱标签走同一管线；把新增部分去掉的版本；在未参与构造干预的数据上的指标。
- **写清几个种子。** 单种子不能判决。
- 探索性运行不必编一个精确假设；写清你要观察什么行为、它如何指导下一步。

---

## 7. 运行前：尺度表

**在设定任何阈值之前**，先建立尺度：

| 指标 | 零模型 | 打乱对照 | 当前基线 | 数据允许的上限 | 拟设阈值 |
|---|---|---|---|---|---|

「零模型」包括随机预测、常数预测、类别先验、`ln C`。「上限」是这个指标在理想情况下的值——如果它满分，你能得出什么结论、不能得出什么结论。

如果不得不在表存在之前设阈值，**明确写「该阈值未建尺度」**。

---

## 8. 报告口径

- **先说决定性的那一点，再给推导、机制或日志行。** 读者要能自己复核，而不是只能相信。
- 每个数字都要带：它取这个值的对照组、分母、来源行。
- **观察与推测分开。** 同一个数字往往有第二个原因（见 `diagnostics.md` §10）。
- 说了要做 ≠ 做了。写清实际执行/排队了什么。
- 不要用「已在 audit 中完成」或一个文件路径代替结论。
- 局部失败（某一步错、测量不足）时，问题的结论是**不确定**，不是「已排除」。
